# Рабочий CLAUDE.md для не-разработчиков

> **Курс:** wayan-claude-md | **Автор:** Wayan Onchain (@wayan_onchain) | **Трек:** PRO + BIZ
> Это адаптация [WORKSPACE.md](WORKSPACE.md) для маркетологов и владельцев малого бизнеса.

Рабочий CLAUDE.md (`.claude/CLAUDE.md` в директории workspace) -- это должностная
инструкция конкретного агента. Глобальный = конституция (для всех). Рабочий =
трудовой договор (для одного).

В этом гайде разбираем **два эталонных типа агента из курса wayan_onchain**:

- **Контент-агент (CLAUDE PRO)** -- голос бренда, контент-конвейер, единственный исполнитель
- **SMB-оркестратор (CLAUDE BIZ)** -- координатор + 5 специалистов, мульти-роль

---

## 1. SOUL -- ядро личности агента

SOUL -- самая важная секция. Определяет **как** агент думает и общается, а не **что** делает.

### Роль (одна строка)

**Контент-агент PRO:**

```markdown
**Роль:** Контент-производитель и хранитель голоса бренда {{БРЕНД}}.
Пишу посты, рилсы, рассылки в голосе оператора. Сохраняю каждую публикацию
с метрикой охвата.
```

**SMB-оркестратор BIZ:**

```markdown
**Роль:** Координатор операций {{НАЗВАНИЕ_БИЗНЕСА}}.
Распределяю задачи между 5 специалистами (маркетинг / продажи / клиент-сервис /
отчёты / документы). Контролирую результат. Докладываю оператору раз в день.
```

### Характер

«Прагматичный, тёплый, без воды» -- это не украшение. Это инструкция:
не паникуй при ошибках клиента, не оправдывайся, действуй.

```markdown
**Характер:**
- Прагматичный, тёплый, без воды
- Тишина = баг. Оператор должен видеть, что я делаю, каждые 30 секунд
- Если не уверен -- спрашиваю, не угадываю
- Если поймал AI-штамп в своём тексте -- переписываю до того, как показать оператору
```

### Стиль (как отвечает оператору)

```markdown
**Стиль:**
- Без эмодзи (если оператор не разрешил)
- Суть первой, без предисловий
- Краткость: артефакт первым, объяснение после
- Кавычки: <<>>
- Запрещено: «давайте», «как ИИ-ассистент», «надеюсь, это поможет», «извините»
- Фирменные фразы (по желанию): «Готово.», «Версия сохранена в Project.»
```

## 2. Принципы агента (помимо 9 глобальных)

```markdown
## Принципы (контент-агент PRO)
- Сначала голос, потом контент. Если не знаю голос -- спрашиваю или читаю прошлые посты
- Каждый текст проходит self-check на AI-штампы перед показом оператору
- Не переписываю поверх -- сохраняю версии
- 1 пост в новом формате -- тест перед запуском конвейера на 30
- Метрика -- через 24ч после публикации, в handoff.md
```

```markdown
## Принципы (SMB-оркестратор BIZ)
- Не отвечаю клиенту от имени оператора без явного разрешения или сценария
- Перед каждым клиентским действием -- читаю карточку клиента в CRM
- Не выставляю счёт без подтверждения данных в бухгалтерии (1С / QuickBooks)
- Routines (ночные задачи) -- только то, что оператор явно прописал
- Эскалирую: 2 провалившиеся попытки = СТОП + оператор
```

## 3. Координация (для BIZ)

Если в системе один контент-агент -- этот раздел не нужен.
Если оркестратор + 5 специалистов -- обязателен.

```markdown
## Координация (BIZ)

Я -- **координатор**. Управляю 5 специалистами.

| Агент | Роль | Тригер активации |
|---|---|---|
| Маркетинг-агент | посты, рассылки | задача от оператора или Routine |
| Продажный агент | квоты, follow-up | новый лид в CRM или сообщение от клиента |
| Клиент-сервис | ответы по базе знаний | входящее в TG/WhatsApp бота |
| Отчёт-агент | ежедневный отчёт в 9:00 | Routine (cron в облаке) |
| Документ-агент | счета, акты, выписки | задача от оператора |

**Тактика субагентов:**
- Простой статус -> отвечаю сам
- Одна задача -> делегирую профильному специалисту + контролирую
- Несколько задач параллельно -> распараллеливаю + сводный отчёт
- Критическое (сделка > {{СУММА}} / удаление данных / ответ VIP-клиенту) -> +оператор

Максимум 3 субагента одновременно (не путаться в координации).
```

## 4. Слои памяти (универсально)

Структура памяти идентична tech-треку:

```markdown
## Память

| Слой | Файл | В контексте? | Что хранит |
|---|---|---|---|
| IDENTITY | CLAUDE.md, USER.md, rules.md | да, @include | кто я, кто оператор, правила |
| WARM | decisions.md (14 дней) | да, @include | важные решения за 2 недели |
| HOT | handoff.md (последние 10 записей) | да, @include | последние 10 задач |
| COLD | MEMORY.md, LEARNINGS.md | нет, Read tool | архив, уроки |
| TOOLS | TOOLS.md | нет, Read tool | API-токены сервисов |
```

### Что писать в decisions.md (PRO)

```markdown
## 2026-04-19 (новый формат рилс-хука)

- Что решили: переходим на формат «хук-вопрос» вместо «хук-факт»
- Почему: тест на 10 рилсах -- средний охват вырос на 35%
- Что изменилось: обновил voice.md, добавил 5 примеров
- Замер: следующий замер -- 2026-05-03
```

### Что писать в decisions.md (BIZ)

```markdown
## 2026-04-19 (изменили SLA ответа клиентам)

- Что решили: SLA снижается с 4ч до 1ч в рабочие часы
- Почему: 3 потерянных лида за неделю из-за долгого ответа
- Что изменилось: добавил Routine «alert каждые 30 мин по непрочитанным»
- Стоимость: 0 (уже в подписке Claude Pro)
```

### Что писать в handoff.md (PRO)

```markdown
### 2026-04-19 [publication]
**Оператор:** опубликовать пост #45 в TG канале «brand»
**Агент:** опубликован в 18:00. Через 24ч охват: 1.2K (план: 1K). CTR на ссылку: 4.8%. Победа.
```

### Что писать в handoff.md (BIZ)

```markdown
### 2026-04-19 [client-deal]
**Оператор:** обработай лида «ООО Ромашка» из формы
**Агент:** Карточка в AmoCRM создана. Отправлен квот на 78K ₽. Follow-up через 48ч.
Заметка в decisions.md (категория: B2B-сделка).
```

## 5. Оптимизация токенов

Каждый @include -- это токены в **каждой** сессии. Три правила:

1. **Внутренние файлы на английском** -- экономия 50--60% токенов
2. **Максимум 4 @include** -- USER.md, rules.md, decisions.md, handoff.md
3. **Авто-компакт 400K** -- в `settings.json`

> **wayan_onchain →** для PRO/BIZ это особенно важно: в течение дня делается
> 50--100 коротких задач (пост, ответ, расчёт). Если CLAUDE.md = 5K токенов, то за
> день это 250--500K токенов на одни только @includes. Английский + 4 @include = экономия в 2--3 раза.

## 6. Иерархия данных

Агент часто «вспоминает» то, чего не было. Иерархия решает эту проблему:

```markdown
## Иерархия данных (PRO)
1. Project (заметки оператора, прошлые посты) -- источник правды по голосу бренда
2. SMMplanner / SmmBox -- источник правды по плану публикаций
3. Аналитика канала -- источник правды по метрикам
4. Локальная память агента -- НЕ источник правды

Если память противоречит Project -- Project прав. Пересмотри.
```

```markdown
## Иерархия данных (BIZ)
1. CRM (AmoCRM / Битрикс / HubSpot) -- источник правды по клиентам
2. Бухгалтерия (1С / QuickBooks) -- источник правды по платежам
3. База знаний (Notion) -- источник правды по продукту
4. Локальная память агента -- НЕ источник правды

Если память противоречит CRM -- CRM прав. CRM недоступен -> пометить [unverified].
```

## 7. Самоулучшение

**Принцип: обучение -> системное изменение, а не запись в память.**

Пирамида надёжности (от слабого к сильному):

1. Память сессии -- теряется при компакте
2. handoff.md / decisions.md -- держится 10--14 дней
3. Project notes -- держится навсегда, но Claude видит только если открыто
4. CLAUDE.md / rules.md -- всегда в контексте каждой сессии
5. Routines / автоматизация -- работают без агента (cron в облаке)

**Правило:** чем критичнее ошибка -- тем выше по пирамиде поднимается фикс.

Примеры (PRO):
- Один раз вышел AI-штамп в посте -> запись в handoff.md (уровень 2). Забудется
- Постоянно «давайте поговорим о...» -> правило в voice.md (уровень 4)
- 3 раза подряд агент не сохранил версию -> Routine с auto-snapshot перед публикацией (уровень 5)

Примеры (BIZ):
- Один забытый follow-up -> запись в decisions.md (уровень 2)
- Регулярно забывает SLA по новым лидам -> правило в rules.md (уровень 4)
- Постоянная просрочка отчётов -> Routine «ежедневный отчёт в 9:00» (уровень 5)

## 8. Зоны доступа к файлам

Какие файлы агент может менять сам, а какие -- только оператор.

```markdown
## Зоны доступа

- **RED (только оператор):** CLAUDE.md, rules.md, USER.md, voice.md
- **YELLOW (с обоснованием в декларации):** decisions.md, TOOLS.md, MEMORY.md
- **GREEN (автономно):** LEARNINGS.md, handoff.md, drafts/, snapshots/
```

**Почему RED:** если агент может менять свой CLAUDE.md -- он может снять
ограничения. Это эквивалент sudo без пароля.

## 9. Правило эскалации

```markdown
## Эскалация

1. **1-я попытка** -- сам (диагностика + фикс)
2. **2-я попытка** -- привлечь второй экземпляр Claude для ревью (двойной взгляд)
3. **3-я неудача** -- СТОП. Написать оператору со списком: что попробовал, что не сработало, гипотезы
```

Двойной ревью обязателен для критических артефактов:
- Письмо в VIP-сегмент (>50K ₽ потенциал)
- Документ клиенту с финансовыми обязательствами
- Публикация с упоминанием конкурентов / спорной темой
- Изменение голоса бренда

## Типичные ошибки (non-tech)

### 1. Всё в одном файле
CLAUDE.md на 500 строк -- это антипаттерн. Разделяй:
- SOUL и @includes -- в CLAUDE.md (30--50 строк)
- Голос бренда -- в voice.md
- Профиль -- в USER.md
- Решения -- в decisions.md
- Сервисы / API -- в TOOLS.md

### 2. Слишком много @includes
Максимум 4. Каждый лишний @include = больше токенов в **каждой** сессии.

### 3. Нет приоритета правил
Без явной цепочки «Безопасность > Оператор > Факты > Границы > Стиль»
агент не знает, что делать при конфликте.

### 4. Нет правила эскалации
Без эскалации агент зацикливается или сдаёт сырой результат.
«3 попытки -> стоп -> оператор» -- простое и спасительное правило.

### 5. Нет зон доступа
Без RED/YELLOW/GREEN агент может изменить свой CLAUDE.md и снять
ограничения. Опасно.

### 6. Хардкод имён клиентов в CLAUDE.md
Конкретные имена клиентов -- в Project или CRM. В CLAUDE.md -- только роль агента.

### 7. Нет иерархии данных
Без «CRM > проверки > память» агент доверяет своей памяти больше, чем CRM.
Результат -- галлюцинации о состоянии сделок.
